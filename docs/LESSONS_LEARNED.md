## 1. Архитектура сессий и мобильные клиенты

### Контекст инцидента
Клиенты мобильных устройств (`mob_1`, `mob_2`) периодически блокировались при смене сети (LTE ↔ Wi-Fi, переключение сотовых вышек) с ошибкой:
```text
🚫 Max sessions reached for mob_1 (1/1), rejecting new connection from <IP>
maximum concurrent sessions limit reached (1/1). please wait for an existing session to close
```
Блокировка длилась 15–20 минут, пока сервер не завершал полузакрытый сокет по системному таймауту TCP.

### Корневая причина (Root Cause)
1. Для мобильного пользователя было задано `max_sessions: 1` и `session_ttl_seconds: 86400` (24 часа).
2. При смене сети со стороны ОС телефона старое TCP-соединение не посылает TCP FIN/RST (тихий обрыв связи).
3. Сервер продолжал считать предыдущую сессию активной (`Active connections: 2`), удерживая единственный слот.
4. В коде отсутствовал механизм вытеснения (eviction) старых сессий — новое подключение безусловно реджектилось.

### Принятое решение & Правило
- **Реализован механизм вытеснения (Session Eviction)** в `core/session/manager.go`:
  - Если лимит `max_sessions` исчерпан, сервер сортирует сессии пользователя по времени создания (`CreatedAt`), принудительно разрывает сетевой сокет старой сессии (`conn.Close()`), отзывает её в BoltDB (`revokeSessionLocked`) и мгновенно подключает новое соединение.
  - Поведение настраивается глобально (`evict_on_max_sessions` в `server_config.json`) и может переопределяться для конкретного пользователя в `users.json`.
- **Lesson Learned:**
  > Любой протокол с ограничением одновременных сессий обязан поддерживать вытеснение (Kick Oldest Session on Reconnect) для мобильных пиров, так как на радиоинтерфейсе обрыв связи в 90% случаев происходит без TCP FIN/RST.

## 2. Утечки горутин и дедлоки в TCP Forwarding

### Контекст инцидента
При длительной работе сервера под нагрузкой росло потребление памяти и количество горутин (`runtime.NumGoroutine()`), которые никогда не завершались.

### Корневая причина (Root Cause)
В обработчике `direct-tcpip` запуск двунаправленной перекачки данных через `io.Copy(channel, targetConn)` и `io.Copy(targetConn, channel)` без механизма одностороннего закрытия (`CloseWrite()`) или отслеживания ошибок приводил к дедлоку: одна горутина завершалась при обрыве, а вторая навсегда зависала в блокирующем чтении из противоположного сокета.

### Принятое решение & Правило
- В `core/ssh/tcp_forward.go` введена синхронизация завершения: закрытие сокета при выходе из первой половины пайплайна разблокирует вторую половину.
- Покрыто регрессионным тестом `core/ssh/tcp_forward_test.go` с гарантией завершения за таймаут (не более 3 секунд).
- **Lesson Learned:**
  > При двустороннем проксировании (`channel ↔ remoteConn`) завершение одного направления обязано принудительно прерывать второе (`conn.Close()`). Полагаться на самостоятельный выход горутины из блокирующего `io.Copy` недопустимо.

## 3. Консистентность индексов сессий в BoltDB

### Контекст инцидента
Файл базы данных `sessions.db` неограниченно рос, а в логах периодически возникали расхождения между списком сессий в бакете `sessions` и индексом `user_sessions`.

### Корневая причина (Root Cause)
Удаление протухших сессий очищало данные из бакета `sessions`, но оставляло ключи в составном индексе `user_sessions` (`username|timestamp|sessionID`), из-за чего курсор BoltDB при проверке сессий натыкался на `nil` и замедлял авторизацию.

### Принятое решение & Правило
- В процедуре `CleanupExpiredSessions` удаление производится атомарно из обоих бакетов в рамках одной транзакции `tx.Update`.
- Покрыто юнит-тестом `core/session/cleanup_test.go`.
- **Lesson Learned:**
  > В K/V базах с вторичными индексами (как BoltDB) удаление сущности всегда должно сопровождаться очисткой всех индексов в той же транзакции. Неконсистентный индекс — источник скрытых утечек памяти и деградации производительности курсоров.

## 4. Защита от DoS и профилирование памяти

### Контекст инцидента
При интернет-сканировании портов SSH злоумышленниками с разных IP-адресов мапа `failedAttempts` в `Guard` бесконечно разрасталась, создавая риск OOM.

### Корневая причина (Root Cause)
Счетчик неудачных попыток (`RecordFailedLogin`) записывал каждый уникальный IP в память, но не имел лимита на максимальное количество записей и фоновой очистки устаревших IP.

### Принятое решение & Правило
- Ограничен максимальный размер кэша попыток в `core/security/blocked_ips.go`.
- Установлен мягкий лимит памяти `debug.SetMemoryLimit(250 * 1024 * 1024)` (250 MiB soft memory limit) в `core/app/server.go`, предотвращающий внезапный OOM-killer от ядра Linux.
- **Lesson Learned:**
  > Любая структура в памяти, ключ которой зависит от внешнего неаутентифицированного ввода (IP, username), обязана иметь верхнюю границу размера (Bounded LRU / Bounded Map).

## 5. Производительность сохранения трафика и Rate Limiting

### Контекст инцидента
При активном трафике вызовы `os.WriteFile` для каждого пользователя на каждую порцию байт создавали избыточный I/O диска и вызывали микрофризы в сетевом потоке.

### Корневая причина (Root Cause)
Синхронная запись на диск в обработчиках сетевых пакетов.

### Принятое решение & Правило
- Внедрен фоновый сборщик `StartAutoSave()` с интервалом `TrafficAutoSaveInterval = 10s`.
- В памяти счетчики атомарно суммируются, а на диск сбрасываются только при изменении с таймером.
- Добавлен чанкинг в `ThrottledWriter` (`core/traffic/ratelimit.go`) для предотвращения зависания при передаче пакетов больше размера burst.
- **Lesson Learned:**
  > Горячий сетевой путь не должен касаться диска. Статистика накапливается в памяти (`atomic` / `sync.Mutex`) и сбрасывается периодическим фоновым воркером.

## 6. Корректность сопоставления доменов и IP (Wildcards)

### Наблюдение / Выявленный риск
В `core/security/access.go` функция `matchesWildcard` использует строковую замену:
```go
regexPattern := strings.ReplaceAll(pattern, ".", "\\.")
regexPattern = strings.ReplaceAll(regexPattern, "*", ".*")
```
и затем делает:
```go
suffix := regexPattern[2:]
return strings.HasSuffix(str, suffix)
```
Из-за этого `suffix` содержит экранированные слэши `\.` (например `\.google\.com`), и проверка `strings.HasSuffix("mail.google.com", "\\.google\\.com")` всегда возвращает `false`.

### Урок & Решение
- Правило `ub-mode`: *Subtract Before You Add*. Не нужно собирать псевдо-регулярки через строковые замены.
- Для доменов достаточно проверять `str == pattern` или суффикс `strings.HasSuffix(str, pattern[1:])` при `strings.HasPrefix(pattern, "*.")`.
- Обязательно покрывать логику белых/черных списков изолированными юнит-тестами.

## 7. Атомарность сохранения состояния и Graceful Shutdown

### Наблюдение / Выявленный риск
1. **Неатомарная запись**: `os.WriteFile` пишет напрямую в рабочий файл `traffic_<user>.json`. При жесткой перезагрузке ОС или сбое питания файл может оказаться усеченным (0 байт или битый JSON).
2. **Отсутствие Graceful Shutdown**: В `core/app/server.go` используется вечный `select {}`. При получении `SIGTERM` от `systemd` процесс моментально завершается без вызова `Flush()` для несохраненного трафика за последние 10 секунд и без закрытия транзакций BoltDB.

### Урок & Решение
- Запись на диск критичных JSON-файлов должна производиться по паттерну: запись во временный файл `file.tmp` → `sync` → атомарный `os.Rename(file.tmp, file)`.
- В `server.go` необходим перехват сигналов `os.Interrupt`, `syscall.SIGTERM` с контролируемым завершением фоновых горутин и вызовом `trafficStore.SaveAllTraffic()`.
